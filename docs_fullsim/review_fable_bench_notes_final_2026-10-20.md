## A. Things that would make the measurements wrong or unusable

**A1 (must-fix, all four notes). "Save config" does not send anything to the board.** In the DAQ the Save config button downloads the configuration text as a file to the browser (frontend/src/App.vue:823–850, a Blob download). The configuration reaches the hardware only when it travels with a command: at Connect (daq.connectHardware(configuration.value), App.vue:432; hardware_runtime.go Connect configures the boards, line 94 of its body) and at Start run (App.vue:967 startRun({configuration, ...}); service/run.go:625 calls Configure). The scans do not take a configuration: the staircase and the hold-delay scan use the plan of the last Configure (hardware_runtime.Configure sets the scan targets, acquisition/hold_delay.go:74–79 writes TriggerMask from that plan, and both coordinators restore that same plan afterwards, acquisition/hold_delay.go:60, acquisition/staircase.go:58). The HV switch of the Hardware tab turns on the voltage of that same applied plan. Consequences as the notes stand:

- Note 1 Setup: HV_Vbias 36.5 V is edited, Save config, HV on in Hardware: the board turns on at the voltage of the configuration loaded at connect (45.4 V if production), and only the first run start reconfigures it to 36.5 V, so the first run begins during the ramp. Same in notes 2 and 3 with 43 V.
- Note 2 steps 2–5: HG_ShapingTime and Tlogic_Mask0/1 are edited, Save config, Start scan: the scan runs with the previous plan (previous shaping and all-channel mask), and the restore after the scan puts that previous plan back. The whole scan series would be taken with the wrong trigger and shaping, silently.
- Note 3 step 3: HV_Vbias lowered, "esperar a que Vmon e Imon estén estables, un run": the new HV is applied by the run start itself, so the wait happens at the old voltage and the run ramps.
- Note 3 step 4 and note 2 step 1 (staircases): run with the plan of the last run, which is fine only if a run was started after the last edit.

Minimal fix, one paragraph in note 0 ("Qué necesita el cocinero" or the mode section) and one line in each Setup: "Los cambios de la pestaña Acquisition llegan a la tarjeta al conectar o al lanzar un run; Save config solo descarga una copia del fichero. Después de cambiar cualquier parámetro (tensión, máscaras, shaping, umbral): lanzar un run corto, esperar a que Vmon e Imon estén estables, y entonces el run bueno o el scan." In note 2, insert "lanzar un run corto" between Save config and Start scan in steps 2, 3, 4 and 5 and after setting TD_CoarseThreshold in step 1; in note 3 step 3, "un run corto para aplicar la tensión, esperar, y el run bueno". The short run can be the 10 000-event run of PRESET_COUNTS or a manual stop; its number goes in the logbook as "aplicar configuración".

**A2 (must-fix, notes 1–3). Per-board indexed lines in the production configuration override the common values.** In JANUS files Parameter[i] is a board index (janusconfig/config.go:18–21), and the production file carries TD_CoarseThreshold[0] = 181, [2] = 179, [3] = 178 and ChEnableMask0/1[0], [1] (test/fixtures/janus/config_same4_v3_good.txt:138–144). If the bench board is board 0, Laura's common TD_CoarseThreshold (note 2 step 1) is overridden by the [0] line. Fix: in the parameter tables of notes 2 and 3 (and note 1 for completeness) add "si la configuración tiene líneas Parámetro[n] para la tarjeta, cambiarlas o borrarlas: mandan sobre el valor común", as already done for ZS_Threshold. HV_Vbias, HoldDelay and the shapings may have indexed lines too.

**A3 (must-fix, note 3). The ladder zero is not below the pedestal for the Citiroc.** Note 3 states twice that the zero of the ladder lies below the menu-1 pedestal because the chain removes the mean dark current (lines 92–98, 216–219, 302). That is the Radioroc2 case. The simulation's own dark_baseline (src/frontend/shaping.jl:228–241) is zero behind a voltage-sensitive preamplifier, because the differentiating stage passes no constant; the Citiroc model is of that kind. The toy of the note shows it: in spe_ptrg.png the 1, 2, 3 pe peaks sit at 1.0, 2.0, 3.0 pe, intercept zero. What does move is the 0 pe population, which in peak stretch is the maximum over the window of the undershoots of earlier pulses plus noise, hence the tail to −1 pe in the figure. Fix the three places: "el cero de la escalera debe coincidir con el pedestal del menú 1 salvo el sesgo del máximo del ruido (unas décimas de ruido, menú 1); lo que baja es el pico de 0 pe, por los rebotes negativos de los DP anteriores. Si el cero sale claramente por debajo, la cadena no es la del modelo." This also fixes "Cero" in "Lo que se espera".

**A4 (must-fix, note 2). The margin rule and the "calibrar con 50 ns" sentence belong to a self-triggered calibration, not to menu 3.** Menu 3 calibrates with PTRG: the window is uncorrelated with the pulses, so the latency and the knee do not enter, and a latency above 31 ns does not prevent calibrating at 25 ns. Note 2 lines 263–267 ("con qué HoldDelay calibrar en el menú 3 ... la calibración se hace con 50 ns") and the margin rule (269–276) contradict note 3, which fixes HoldDelay = 200 ns a priori and says so (lines 76–78). Fix: in note 2, "dice con qué HoldDelay mínimo tomar las medidas de energía (donde el trigger es el evento) y comprueba que los 200 ns del menú 3 contienen el máximo en los tres shapings"; keep the margin rule but address it to the energy runs; delete "la calibración se hace con 50 ns".

**A5 (checked, correct). The trigger restriction and the staircase side effect work as described.** BunchTrgSource TLOGIC maps to the trigger-logic bit (dt5202/config.go:275), TriggerLogic OR64 to logic 0 with the majority in the same register (config.go:307, 543), and Tlogic_Mask0/1 go to the time-discriminator mask registers that the FPGA applies before the logic (config.go:372–376, 547; FERS_configure_5202.c:222–224 "applied in FPGA"), so with TLOGIC + OR64 + one bit only that channel triggers. The masks in note 2 are right (channel 20 = 0x00100000, channel 40 = bit 8 of Mask1 = 0x00000100, channel 60 = 0x10000000). The staircase writes CitirocConfig = 0x00070f20 (staircase/scan.go:60–71), which is fast shaper on the high gain, peak detector, charge discriminator direct, and the restore applies the plan, which does not contain CitirocConfig before PR #73 (dt5202/config.go has no such write), so the value persists until a power cycle or a JANUS session; the note's precaution is correct. The staircase also sets both shaping registers to 25 ns and the trigger and output masks during the scan, all restored by the plan. The scan limits are within the DAQ's bounds: steps multiples of 8, 10 to 100 000 events per delay, timeout 1 s to 10 min, at most 64 points (holddelay/scan.go:46–60, MaxPointCount = 64); 0–248 in 8 and 0–496 in 16 are 32 points each. Staircase: thresholds 0–2047, dwell 1 ms to 34 s, at most 4096 points (staircase/scan.go:42–55); 150–300 in steps of 1 at 500 ms is 151 points, 76 s. The hold-delay scan requires SPECTROSCOPY in the plan and the ready state (acquisition/hold_delay.go:52; service/scan_hold_delay.go), which exists after a run. The UI labels used (Scans, Hold-delay scan, Staircase, Start scan, Minimum, Maximum, Step, Events / delay, Timeout (s), Dwell (ms), Board) exist in HoldDelayWorkspace.vue and StaircaseWorkspace.vue; the Board selector must be set to the bench board (not mentioned, optional).

**A6 (must-fix, note 2 table). BunchTrgSource/TriggerLogic restore.** "Al terminar" says to restore BunchTrgSource and TriggerLogic to their starting values; production is TLOGIC with MAJ64 and majority 4, and MajorityLevel is not in the table. If TriggerLogic is set to OR64 and MajorityLevel left at 4, the DAQ still writes majority 4 into the register with logic OR64; FERSlib ignores the majority for OR64, so it is harmless, but say "MajorityLevel: dejar el de producción" to avoid the question. Optional otherwise.

**A7 (optional, note 0). T0_Out = T-OR with the mask.** Tlogic_Mask is applied to the time-discriminator inputs in the FPGA, so T-OR is probably masked too, but TLOGIC certainly is; set T0_Out = TLOGIC with TriggerLogic OR64 (both accepted, config.go:291–292, 307) for the LG trigger, the same configuration as menu 2. And after A1, the change needs a run start to reach the board, which the oscilloscope procedure already has ("lanzar un run ... dejarlo corriendo").

## B. Physics and the figures

**B1 (must-fix, note 2 Figure 1 and Análisis).** scan_ps.png plots the mean stored value, which has no sharp knee at 50 and 87.5 ns because crosstalk (mean 1.2 pe) and pile-up keep it rising to 1.6 pe at 200 ns; the knee is visible in the position of the 1 pe peak, which is what the Análisis uses (line 323–326). Either add the peak position to the figure or say in the caption that the knee is read on the 1 pe peak, not on the mean, and that the slow rise of the mean after the knee is pile-up (as line 74–75 says).

**B2 (must-fix, note 3 caption and Análisis). "El borde derecho afilado".** With noise 0.11 pe at 25 ns and the peak-stretch bias of the maximum, the right side of each peak in spe_ptrg.png is a noise-smeared edge, not a sharp one, and "la posición de cada pico es su borde derecho" is not an estimator a student can apply. Define it: the mode of each bump (or the half-height point of its right side), the same estimator applied to the simulated spectrum. The ladder spacing is insensitive to the choice as long as data and model use the same one.

**B3 (optional, note 3). The toy's dark rate at 3 V.** The model scales the dark rate with the PDE (src/frontend/sipm.jl:132–135), nearly flat between 3 and 5 V, hence 4.3 and 4.4 MHz (VOV in citiroc_spe_figs.py:21). Real devices show the rate growing with overvoltage, so the 1 pe plateau at 3 V may come out well below 4.3 MHz; say "según el modelo" and that a lower value is expected to be the first thing the data correct.

**B4 (checked, correct).** Note 1 Section 1 after the revision: window = HoldDelay, latency shifts its start; ventana.png regenerated with OFFSET = 0 (hold_scan_figs.py:212), 2.2 and 1.6 at 296 ns match the single-sample-at-zero premise; the (87.5/t_p)^0.5 law and 0.06/0.08/0.11 pe at 5 V consistent with citiroc.jl:37–40, 90 (with the caveat, already in the note, that noise_pe is fixed in avalanches at the configured 3 V). Note 3 gains: 0.93 × 10⁶ e/V, 4.6, 3.7, 2.8 × 10⁶ and 0.75 pC at 5 V consistent with the S14160 datasheet point (2.5 × 10⁶ at 2.7 V). Crosstalk ratios 0.20, 0.28, 0.32, 0.35 at 5 V and 0.09, 0.13, 0.15, 0.17 at 3 V agree with staircase_crosstalk.png; the 10 pe plateau near 250 Hz is consistent with a Borel tail of λ = 0.217, so 500 ms per point gives about 120 counts. PTRG ladder: P(at least one pulse peak in 200 ns) = 1 − exp(−0.88) = 58%, "unos dos de cada tres" is fair; the method is indeed independent of threshold, fast shaper and latency since the trigger is not the pulse. Note 2: 1 pe plateau 4.4 MHz and 2 pe five times lower (0.195) consistent; HV 43 V for 5 V at 38.0 V breakdown; knees 31, 58, 90 ns minus latency consistent with the revised premise.

**B5 (optional, note 2 line 95–102).** "La latencia es de la FPGA y la misma para los 64 canales" is right; "el tiempo hasta el máximo lo fija el shaping, común a los 32 canales de cada chip" is right; but the 2–3 pe pulses triggering 5–6 ns earlier (walk) is also why the 1 pe peak and the mean move differently; it is already in the margin rule, fine.
