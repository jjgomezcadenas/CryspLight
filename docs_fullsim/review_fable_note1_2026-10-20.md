# Referee report: bench note 1 v2, pedestal and noise of the Citiroc (bench/1_citiroc_noise_v2.tex)

Date: 2026-10-20. Read-only. Sources: the note and note 0, the simulation (src/frontend/citiroc.jl, shaping.jl, fullsim_runs/2026-10_ambient/frontend_bgo_citiroc.toml), pet-caen-daq at 75086b2 (janusconfig/catalog.go, dt5202/config.go and pedestal.go, hdf5store/writer.go, service/preset_stop.go, frontend/src/App.vue), FERSlib 5.0.1, the Citiroc 1A datasheet text. Numbers come from short estimates with the toy's noise model (shaped white noise, correlation time about the peaking time); they are indicative.

## Summary

The plan is sound and the DAQ side is correct: every parameter name and value exists in the catalogue with the meaning the note gives it, zero suppression at 0 is disabled, the files, table and columns are as stated, the tabs and buttons exist. The physics needs three corrections. First, HoldDelay = 0 is not a single sample: the peak detector is armed at the trigger and held a latency L later, so even at 0 the stored value is the maximum of the noise over L, which narrows the pedestal and biases it up by amounts that depend on the shaping; the "gain-free test" ratios 1.32 and 1.87 will come out smaller than predicted (roughly 1.2–1.3 and 1.5–1.7 for L of 50 ns) unless the comparison is made with the simulated maximum over L + HoldDelay, with L fitted from the step-2 points. Second, the note says the step-2 pedestal is "the one the energy runs will see": only its electronic part; above breakdown the peak-stretch pedestal is dominated by the dark pulses, which this menu excludes by design. Third, the expected values are consistent with the simulation only under the statement "the noise is fixed in charge", which the physics supports but the code does not implement: the simulation holds noise_pe fixed in avalanche units at the configured operating point, so a simulation at 5 V must set noise_pe = 0.06 by hand. Two runs should be added (HoldDelay 300 ns, the production value, and a repeat of one setting at the end for stability), and a few student-facing details fixed.

## 1. Physics

**What the simulation needs.** The model has one free noise parameter, noise_pe = 0.1 at noise_tp_ns = 87.5 (citiroc.jl:37–39; the ambient TOML line 29), scaled as (87.5/t_p)^0.5 (noise_at, citiroc.jl:90), and the low-gain noise equal in ADC counts to the high gain at the same peaking time (lg_noise, citiroc.jl:91–92, default lg_noise_pe = 0). The plan measures exactly these three things, plus the window dependence that the peak detector adds (design note lines 596–602). Good.

**Expected values.** 0.1 pe at 3 V is 0.06 pe at 5 V if the noise is fixed in charge (gain proportional to overvoltage: 2.5 × 10⁶ at 2.7 V for the S14160, so 1 pe at 5 V is 1.67 times the charge at 3 V; 0.1/1.67 = 0.06). The ratios are (87.5/50)^0.5 = 1.32 and (87.5/25)^0.5 = 1.87, and 0.06 × 1.32 = 0.08, 0.06 × 1.87 = 0.11. All consistent with the model as stated. Two caveats to write into the note: (i) the code does not rescale noise with overvoltage; noise_pe is in avalanches at the configured op (overvoltage_v = 3.0 in the TOML), so a run simulated at 5 V with the same file would have 0.1 pe, not 0.06; whoever compares must set noise_pe = 0.06 at 5 V, or compare in ADC counts; (ii) the simulation's adc_per_pe is 10 counts per avalanche at 3 V (TOML line 30), so its pedestal rms is 1 count at 87.5 ns and 1.9 at 25 ns; the real board's high gain is tens of counts per photoelectron at 5 V, so the bench will see σ of a few counts. In both cases the Gaussian is only a few ADC codes wide: fit with 1-count bins and apply Sheppard's correction (σ² − 1/12) if σ is below about 2 counts.

**HoldDelay = 0 is not zero window.** FERSlib arms the peak detector from the external global trigger and holds it HoldDelay after gtrg (FERS_configure_5202.c:245, 254; datasheet: track phase until trigger, peak detection until hold). The arming itself reaches the chip a latency L after the PTRG edge that nobody has measured (tens of ns is plausible). At HoldDelay = 0 the stored value is therefore the maximum of the noise over a window of length L, and "el valor guardado se acerca al ruido en un instante" (line 126–128) holds only if L is short compared with the noise correlation time, about one peaking time. For shaped white noise the maximum of N effectively independent samples has mean 0.56, 0.85, 1.03 σ and rms 0.83, 0.75, 0.70 σ for N = 2, 3, 4; for a 100 ns window I find +1.7σ and 0.60σ at 25 ns shaping, +0.9σ and 0.81σ at 87.5 ns. With L around 50 ns the pedestal width at 25 ns shaping underestimates σ by 15–25% and at 87.5 ns by 5–10%, and the ratios of the "prueba sin ganancia" fall from 1.87 and 1.32 to roughly 1.5–1.7 and 1.2–1.3. This is not a flaw of the measurement, which is the right one, but of the expectation. Corrections: (a) state that step 1 measures the shortest available window, not one sample; (b) fit L from the step-2 window dependence (widths at 0, 96, 200 ns, which the simulated maximum-over-window reproduces as a function of L + HoldDelay) and then quote σ from the fit, not from the 0 ns width; (c) compare ratios and widths with the simulated peak-stretch pedestal at the same L + HoldDelay, which the simulation produces directly (design note 1066–1068). The design note's own value for the comparison is "the random-trigger pedestal", so this is a change in the analysis, not in the model.

**Points 96 and 200 ns.** Fine as a pair that brackets the model's peaking times, with one addition: the production configuration holds at 300 ns (test/fixtures/janus/config_same4_v3_good.txt:111), so add HoldDelay = 300 ns, which is the window the energy runs will have. The step-2 runs are at HG 25 ns, but each run also records the low gain at 87.5 ns (LG_ShapingTime fixed), so the LG pedestal versus window at the energy shaping comes free from the same three or four runs; say so, because the energy is read on the low gain and this is the pedestal that matters most. If time allows, repeat the 300 ns point with HG 87.5 ns.

**"The pedestal the energy runs will see" (line 82–84).** Only its electronic part. Above breakdown the peak-stretch pedestal of a channel without light is the maximum over the window of a dark train at several MHz plus noise (design note 602–604), and the chip removes the mean dark current, about 0.6 pe at 87.5 ns and 4.4 MHz, so the zero shifts as well. That pedestal is measured in menus 2 and 3 with PTRG above breakdown; rephrase the sentence to "la parte electrónica del pedestal".

**Below breakdown, 1–2 V.** Safe and sufficient. Below V_br there is no Geiger multiplication, so no dark pulses; the terminal capacitance, which sets the series noise, is that of a depleted junction and changes by a few percent between V_br − 1.5 V and V_br + 5 V, below the precision of this measurement. The breakdown spread within a Hamamatsu array is a few tenths of a volt, and between 20 and 28 °C the breakdown moves from 38.2 to 37.9 V, so 36.5 V keeps every channel 1.2–1.8 V below. HV_IndivAdj = 0 in the production configuration (fixture line 23), so "si HV_IndivAdj no resta nada" is the actual case; say so instead of leaving it conditional. The precaution of looking for a 1 pe peak is the right check; add the reverse one: if a channel shows a width far above the others, it may be oscillating or picking up noise, which is information, not a failure.

**10 000 events.** Enough: the statistical error of σ is σ/(2N)^0.5 = 0.7% and of the mean 1% of σ, per channel; 10 s of beam time. 50 000 would cost 50 s and help the tails and the outlier channels; the count is total over the boards in the run (service/run.go:864 counts pipeline events), so with more than one board in the plan each board gets its share.

## 2. DAQ correctness

All names in the table exist in the catalogue (janusconfig/catalog.go): HV_Vbias, HV_IndivAdj (28–29), AcquisitionMode, BunchTrgSource (32), PtrgPeriod (39), ChEnableMask0/1 (42), GainSelect, Pedestal (48–49), ZS_Threshold_HG/LG (50), StopRunMode, PresetCounts (59–61), HG/LG_ShapingTime, HoldDelay, HG/LG_Gain. Values: SPECTROSCOPY is mode 1 (config.go:204); PTRG is a valid BunchTrgSource; GainSelect BOTH gives both energies per channel; ZS_Threshold 0 is written as register 0, which disables zero suppression, exactly as FERSlib does (pedestal.go:53–55; FERS_configure_5202.c:274–277), so "sin zero suppression" is right and the per-channel ZS_Threshold_HG[i]/LG[i] lines of the production file must also be 0 or absent, which the note should say. ChEnableMask0/1 all ones; "Configure channels" and "Enable all" exist in the UI. StopRunMode PRESET_COUNTS with PresetCounts 10000 is parsed by service/preset_stop.go:40–46 and stops the run on the event count. "Store run histograms" is a checkbox in the RunCtrl section of the Acquisition editor (App.vue:1462–1468) and writes run_<id>.histograms.h5 (hdf5store/run.go:128); the decoded file is run_<id>.0000.h5 (runpipeline/storage_hdf5.go:15, one segment per 0000 index; a long run adds .0001 and so on). The table is events/spectroscopy/observations (writer.go:224, validate.go:66) with the columns channel, high_gain, low_gain (writer.go:740–747) plus has_high_gain, has_low_gain, discriminator, trigger_id, timestamp and the rest; one row per event and channel. The configuration goes into the file (hdf5store/configuration.go: the set voltage voltage_v, not the monitor), and the monitored HV voltage, current and the board temperatures go into events/service rows (hdf5store/events.go:48–60), which exist only if service events are enabled (EnableServiceEvents); the note should ask that they be on, since the logbook relies on "la temperatura y la tensión están también dentro de los ficheros". Tabs: Acquisition, Statistics, Plots, Scans, Hardware, Runs (App.vue:73–78); Save config exists; the Runs tab lists each run's artifacts with a Download action (RunHistoryTable.vue:255), so the commented-out lines 91–93 are correct and can be restored. The Hardware tab shows HV voltage, current and HV temperature per board (App.vue:2092–2101), which is where "Vmon e Imon" are read.

The run histograms are 4K bins over 8192 codes by default (service/histogram.go:18–24), two codes per bin: too coarse for a σ of a few counts. The note already analyses the event table; say explicitly that the histogram file is for a look in Plots only.

## 3. Where a student would trip

- HV_Vbias 36.5 V is below the production value (45.4 V in the fixture, line 20); the note should say the production configuration is the starting point and only the listed parameters change, and that the HV must be set before the run, not changed during it.
- PtrgPeriod 1 ms with PresetCounts 10 000 gives a 10 s run; a run that ends before the operator looks at Plots is normal. Say that the check of the precaution is done on the stored histograms of the first run.
- The HG_Gain value: "los valores de la configuración de partida" is 55 (fixture lines 104–105); write the number, since the conversion to photoelectrons in menu 3 depends on it.
- State that LG_ShapingTime = 87.5 ns in every run means the low-gain pedestal versus window is taken at the energy shaping in step 2, and name that as a result.
- Add HoldDelay = 300 ns to step 2 and, at the end, a repeat of the first run (HG 25 ns, HoldDelay 0) for stability of the pedestal across the session and the temperature.
- Order of the HG_ShapingTime runs: the note goes 25, 50, 87.5; fine, but each change requires Save config and a new run; say that the run number changes and goes in the logbook with the shaping.
- The analysis bullet "la media (pedestal) y la anchura (ruido)" should say "la anchura menos la corrección de ventana" or point to section 1 of this report, so the student does not report the 0 ns width as σ.
